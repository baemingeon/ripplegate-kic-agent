## 단계별 실행

### 1. 예선 제출 잠금 — 11/7~11/11

범위를 더 넓히지 않고 `기업 1개·Peer 3개·멀티플·Evidence Ledger·재계획·보류`를 고정한다. Tool 사전·사후조건 trace와 KIC 공개위원회 접점 문구를 기준으로 팀 정보 입력 후 PDF를 다시 생성하고, validator·PDF 페이지 수·접수 화면을 확인한다. 제출은 11/12 09:30 이전 완료를 목표로 한다.

### 2. 본선 준비 선행 — 11/12~12/2

예선 결과를 기다리는 동안 코드 저장소 구조, 실행 README, 공개자료 라이선스 기록, 데모 환경, fallback 영상을 준비한다. 동일 packet 수작업/Agent 시간, 재작업 횟수, 출처 누락, 계산 불일치를 측정하고 실제 입력 전에는 `AWAITING_HUMAN_PAIRING` 상태를 유지한다.

### 3. MVP 안정화 — 12/3~12/9

상위 12팀 진출 시 공개 데모 URL을 먼저 안정화한다. 기능 추가보다 90초 핵심 흐름을 고정한다.

`입력 → Planner 계획 → Tool allowlist → 근거 조회 → 정규화 → 계산 → 검증 → Reflection → IC 메모`

정상 케이스는 `ready_for_review`, 충돌 케이스는 `REPLAN`, 미해결 케이스는 `HOLD`, 모델 장애는 deterministic fallback으로 끝까지 실행되어야 한다.

### 4. 신뢰성·확장성 증명 — 12/10~12/16

3~5개 기업과 신규 오류 표현을 추가한다. 가격 지연·부분 데이터·API 실패·기간·통화·단위·주식수 기준·사업모델 불일치를 각각 평가한다. LLM은 계획과 Reflection만 제안하고, Calculator·Verifier·승인 게이트는 결정론적으로 유지한다. 특정 국가의 로컬 모델을 필수 구성으로 두지 않는다.

### 5. 발표·코드 패키징 — 12/17~12/21

10분 발표 PDF를 별도로 만든다. 구성은 `문제 1분 → 실제 시연 4분 → Agent 판단 Trace 2분 → 신뢰성·평가 1분 → 활용·확장 1분 → 마무리 1분`으로 고정한다. GitHub fresh clone 실행, 데모 URL, 녹화 fallback, Q&A 답변을 서로 대조한다.

### 6. 최종 제출·발표 — 12/22~12/29

12/22 09:30 이전에 제출을 완료하고 접수 상태를 캡처한다. 발표 전날에는 실시간 데모보다 녹화 fallback과 동일한 결과가 나오는지 확인한다. 질의에는 `전부 HOLD`, `동일 LLM 검증`, `오류 주입`, `시간 절감`, `내부자료 반출` 순서로 답한다.

## 본선 통과 기준

| 게이트 | 통과 기준 | 증거 |
|---|---|---|
| 실행 완성도 | fresh clone·데모 URL·fallback 모두 실행 | GitHub README·영상·run log |
| Agent 기술성 | Planner 제안, allowlist, Replan, Reflection, 상태 Trace 노출 | UI Trace·raw log |
| 결과 신뢰성 | 근거 클릭, 계산 재현, unresolved이면 HOLD | Evidence Ledger·Verifier log |
| 사용성 | 입력부터 다음 행동까지 90초 내 이해 | 사용자 시나리오 녹화 |
| 활용성 | 시간·재작업·누락·불일치 측정 | stopwatch sheet·review log |

## 절대 금지

- KIC 내부 SOP·담당자·시간절감 수치를 확인한 것처럼 쓰지 않는다.
- observable policy 통제군의 100%를 live LLM 일반화 성능으로 표현하지 않는다.
- 실제 실행되지 않은 URL·GitHub·모델·데이터 사용을 기재하지 않는다.
- 예선 PDF와 본선 발표 PDF, 편집용 PPTX를 서로 다른 주장으로 관리하지 않는다.

효과 수치 잠금: `python .\mvp\validate_effect_measurement.py --strict`가 `READY_TO_REPORT`가 되기 전에는 시간절감률을 발표하지 않는다. 서버 실행시간은 사람 업무시간이 아니다.
