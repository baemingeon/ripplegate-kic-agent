# IC Preflight 정본 마스터 플랜 v1.1

작성 기준일: 2026-11-07

이 문서는 예선 기획서, 본선 MVP, 발표 시연을 하나의 기준으로 묶는 현재 정본이다. 이전 버전의 서비스명·모델 실험·benchmark 문서는 작업 기록으로만 보관한다.

## 1. 한 문장 포지션

**IC Preflight는 KIC의 투자 판단을 대신하는 시스템이 아니다. 투자심의 전에 자료·수치·리스크의 기준이 맞는지 확인하고, 문제가 남으면 추가자료 또는 보류로 넘기는 품질 게이트다.**

KIC 공개 자료는 투자 목표 설정부터 거시경제·자본시장 분석, 자산배분, 운용계획, 실행, 모니터링까지의 전체 투자 프로세스를 설명한다. IC Preflight는 그 프로세스보다 우수하다고 주장하지 않는다. 공개된 위원회 검토 전에 검증 packet을 준비하는 보조 레이어로 제안한다.

서비스명 선택 이유: `IC Preflight`는 Investment Committee 전에 수행하는 사전 점검이라는 뜻이다. KIC의 공식 명칭을 무단으로 포함하지 않으면서도, 투자 결론이 아니라 검토 전 자료·수치·근거를 확인하는 제품 위치를 한 번에 전달한다.

공식 근거:

- KIC [투자 프로세스](https://www.kic.kr/ko/investment/process)
- KIC [리스크 관리](https://www.kic.kr/ko/investment/risk-management)
- 공모전 [공식 안내·제출 규정](https://daker.ai/public/hackathons/kic-ai-agent-competition)

## 2. 심사위원이 기억해야 할 장면

심사위원 입력 문장:

> 대상 기업의 FY2025와 비교기업의 9M FY2026 실적을 비교해줘

IC Preflight의 기대 흐름:

`PLAN → 자료 조회 → 기준 확인 실패 → 원문 재조회 → 해결 근거 없음 → HOLD`

동일 입력의 일반 답변 비교군은 `REVIEW`로 끝난다. IC Preflight는 기간이 다른 숫자를 계산하지 않고, 보류 이유와 다음 행동이 있는 투자심의팩을 남긴다. 이 한 장면으로 단순 검색·요약과 Agent의 차이를 설명한다.

## 3. Agent 구성의 기준선

| 구분 | 담당 | 반드시 남겨야 하는 증거 |
|---|---|---|
| 목적 해석 | Controller / 선택형 Planner | 사용자 목표, 기준일, 필요한 지표 |
| 자료 수집 | Retriever / 공개자료 Adapter | URL, 문서, 페이지, 기준일, fingerprint |
| 기준 정리 | Normalizer | 기간·정의·통화·단위 상태 |
| 검증 | 결정론적 Verifier | 통과·실패 조건, 미해결 이슈 |
| 재계획 | Controller | 재조회·재계산·추가자료·보류 중 선택한 이유 |
| 계산 | Decimal Calculator | 입력 숫자, 공식, 결과, 민감도 |
| 반대 검토 | Critic | 취약 가정과 반대 근거 |
| 종료 | Human handoff | 진행·추가자료·보류, 담당자 다음 행동 |

LLM은 계획·질의·설명 제안만 맡는다. 숫자·출처·계산·최종 보류 판정은 결정론적 모듈이 맡는다. 기본 MVP는 모델 없이 실행하며, 모델을 연결할 때는 승인된 private/OpenAI-compatible endpoint와 model allowlist를 사용한다.

## 4. 예선 점수 상승표

아래 점수는 공식 점수가 아니라, 현재 제출물과 확인된 증거를 기준으로 한 내부 감사표다.

| 항목 | 배점 | 현재 상태 | 만점에 필요한 마지막 증거 |
|---|---:|---|---|
| 문제 정의·주제 적합성 | 20 | 업무 위치와 오류 유형을 명확히 제시 | 실제 사용자 1~2명 또는 관찰 가능한 업무 packet으로 Before 확인 |
| AI Agent 구성·설계 | 25 | 경로 선택, Tool allowlist, 재계획, 안전 게이트 구현 | 승인 gateway 실행 trace 또는 공개 데모에서 계획·재계획 장면 고정 |
| 차별성·창의성 | 20 | 같은 입력의 REVIEW/HOLD 비교와 근거 ledger 제시 | 처음 보는 표현·정상 케이스를 포함한 holdout 결과 공개 |
| 실현 가능성 | 20 | 10페이지 기획서와 실행 가능한 MVP, 반복 테스트 보유 | 데모 URL, GitHub 재현, 장애 시 예비 영상 확보 |
| 활용성·확장성 | 15 | 심의팩·담당자 handoff·자산군 Adapter 구조 제시 | 같은 packet의 실제 시간·재작업·출처 누락 측정 |

현재 주장 가능한 수준은 “만점 확정”이 아니라 **실행·증거 구조가 갖춰진 예선 통과권 후보**다. 사용자의 팀 정보, 실제 수작업 시간, 공개 Demo/GitHub 링크가 들어오기 전까지 그 수치를 과장하지 않는다.

## 6. 남은 입력과 처리 순서

### 사용자가 반드시 입력할 것

1. `기획서/team_info.template.json`을 `team_info.json`으로 복사하고 팀명·팀장·팀원·연락처를 입력한다.
2. 본선 진출 시 실행 가능한 Demo URL과 GitHub URL을 입력한다.
3. 같은 자료 packet을 기준으로 수작업 작성시간과 Agent 작성시간을 각각 측정한다.
4. 실제 사용 예정 데이터·모델·API의 라이선스와 내부 반출 정책을 확인한다.

### 제출 직전 자동 확인

```powershell
python .\mvp\test_mvp.py
python .\mvp\validate_submission.py
python .\mvp\validate_release.py
```

`READY_AFTER_USER_INPUT`은 코드 실패가 아니라 팀 정보·외부 링크·실제 효과 측정이 아직 입력되지 않았다는 뜻이다. 제출 전에 이 세 가지를 채워야 한다.

## 7. 본선 10분 발표 흐름

| 시간 | 보여줄 것 | 한 문장 |
|---|---|---|
| 0:00–0:40 | 문제와 사용자 | 기준이 다른 숫자를 계산하는 순간 심의자료의 신뢰가 흔들린다 |
| 0:40–1:30 | KIC 접점 | 기존 투자 프로세스를 대체하지 않고 검토 전 품질을 확인한다 |
| 1:30–3:00 | 한 문장 입력 | 기간이 다른 자료는 먼저 확인하고, 풀리지 않으면 멈춘다 |
| 3:00–5:00 | 실행 화면 | 일반 답변 REVIEW와 IC Preflight HOLD를 같은 입력에서 비교한다 |
| 5:00–7:00 | Trace와 심의팩 | 계획·Tool·검증·재계획·근거·다음 행동이 한 기록에 남는다 |
| 7:00–8:30 | 신뢰성·보안 | 결정론적 게이트, allowlist, private endpoint, human handoff |
| 8:30–9:30 | 효과와 확장 | 시간·재작업·출처 누락을 측정하고 자산군 Adapter로 확장한다 |
| 9:30–10:00 | 한계와 요청 | 공개자료 MVP이며 내부 SOP와 효과 수치는 검증 후 확대한다 |

## 8. 절대 하지 않을 주장

- KIC 내부 SOP를 재현했다고 말하지 않는다.
- 모든 LLM보다 우수하다고 말하지 않는다.
- 오류 주입 결과를 일반화된 AI 정확도로 포장하지 않는다.
- 서버 실행시간을 분석가 시간절감으로 바꾸어 말하지 않는다.
- 모델이 모든 숫자를 계산하거나 투자 승인을 대신한다고 말하지 않는다.

## 9. 완료 조건

다음 항목이 모두 참일 때만 제출 완료로 판정한다.

- 팀 정보가 표지와 제출 계정에 일치한다.
- PDF가 공식 7개 구성과 10페이지 제한을 만족한다.
- 재현 문장으로 PLAN·VERIFY·REPLAN·HOLD가 실제 실행된다.
- 일반 답변 REVIEW와 IC Preflight HOLD 비교가 화면에 남는다.
- Evidence Ledger의 출처가 원문으로 연결되고 감사 로그를 다운로드할 수 있다.
- LLM 장애·endpoint 불가·allowlist 실패에서도 안전 게이트가 종료된다.
- Demo URL과 GitHub에서 같은 버전의 MVP가 실행된다.
- 실제 효과 측정은 측정값과 측정방법을 함께 공개한다.
